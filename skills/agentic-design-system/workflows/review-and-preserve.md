# Review and preserve (experimental)

Explicit opt-in only. This is a candidate working mode inside ADS, not a new skill, default,
installation instruction or demonstrated design improvement. Record selection in the existing task
brief; do not create another orchestration layer. To stop using it on a later task, omit the selection.
Existing project rules and the user's requested outcome still govern.

Example selection: "Use ADS review and preserve for this task. Keep the first design's useful
composition and identity while fixing observed problems."

## Understand: establish the real constraints

Recover the user job, content, output, existing product language, references and required states.
Keep explicit brand/taste decisions, tokens, component APIs and accessibility requirements. A fresh
page is not permission to ignore them. For an existing surface, inspect its current rendered state
and source; that is the baseline, not a newly invented replacement.

For a fresh surface, build the first candidate from that brief and context. Do not automatically
choose a generic aesthetic preset, perform a style-ban sweep or load unrelated craft references
before it exists. This is not "ignore design": composition, hierarchy, readable type, responsive
behavior, semantic controls and the intended task are part of the first build. Resolve meaningful
unknowns from available sources; do not manufacture an approval or questionnaire when ordinary
judgment suffices. Explicit requests for exploration or a visual target still get their relevant route.

## Choose and work: preserve strengths, repair actual problems

Inspect the rendered whole at the target desktop and phone surfaces. In the existing task notes,
briefly name the useful composition, grouping, typography, spacing rhythm, density, identity and
task flow that must survive. Name actual weaknesses separately. This is a short preserve list,
not another scoring rubric, template bundle or demand for the user to diagnose the design.

An initial candidate is not automatically good. Missing task content, a poor hierarchy or a broken
flow can justify a structural change. Record why and which useful parts remain; preservation is
not a veto on necessary redesign or the user's explicit requested change.

For each consequential repair, connect the observed issue to the smallest relevant change and the
strength it must preserve. Load specialist guidance to answer that specific issue, rather than
running every specialist as a serial stage. Group related fixes within the existing task budget.

Containers, flat sections, typography, color and whitespace are means to an understandable whole.
Do not flatten meaningful groups, reduce hierarchy or add helper/status chrome just to resemble a
generic house style. Equally, do not retain decoration, excessive nesting or clutter merely because
it was in the first candidate. Neither adding nor removing cards is a success metric.

## Prove: required checks still apply

Exercise applicable state, keyboard, semantic, contrast, responsive and interaction behavior.
Retain permissions, destructive-action boundaries, source truth, licensed assets and truthful
prototype scope. Keep effective touch targets and legibility; a denser screenshot is not grounds
to reduce usability. The original mode's tool, spending and delivery approvals are unchanged.

Use matched baseline/after views and affected interactions. Compare the whole design as well as
individual fixes: reading order, grouping, hierarchy, density, visual identity and action clarity.
If a repair solves a local defect but weakens the whole, revise that repair within the same budget.
Do not roll back a necessary accessibility or behavior fix merely because the old page looked
better. Find a compatible repair or report the unresolved tradeoff. Missing browser access remains
unverified, not permission to substitute a source scan for rendered evidence.

### Scope of aesthetic rules in this opt-in mode

Foundation profiles remain context, not mandatory typography/palette choices. Generic aesthetic
findings are report-only here: border/shadow treatments, casing, punctuation, status-dot styling,
typographic convention, icon style and divider density. This is an explicit experimental exception
to default-mode aesthetic `never` readiness gates, not a change to the stored Foundation contract.

Do not waive explicit user/project requirements or required functionality, semantics, legibility,
contrast, focus, effective targets, content visibility or status readability without color. For
example, a dot alongside readable status text is not rejected merely for being a dot; a status
encoded only by color still fails. Authored uppercase may remain if it serves the actual brief;
clipped, illegible or semantically incorrect content still needs repair.

Keep raw scanner/capture findings unchanged and disclose the selected mode beside the verdict.
Never relabel a failed automated check as passed. If a required external release gate enforces a
conflicting aesthetic rule, report that release blocker rather than bypassing it. The mode does
not grant merge, publication, deployment, project-rule changes or global-install authority.

## Decide: no regression certificate from a checklist

Use the existing brief and consolidated findings. Required task or usability failures remain open;
aesthetic suggestions do not force repairs unless supported by the brief or an observed problem.
A technical pass cannot compensate for a weaker overall design. If the budget ends with a material
tradeoff unresolved, retain the candidate and state it; do not restart, escalate models or add judges.

Ember reads the evidence already collected for the normal substantial handoff. Do not claim its
receipt is independent taste approval. Separate verified behavior, parent visual judgment and
actual user acceptance. A mode-ready candidate is not automatically installed, released or proven
better than vanilla. No additional paid review or generation is implied by selecting this mode.
