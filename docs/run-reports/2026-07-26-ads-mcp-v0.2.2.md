# ads-mcp v0.2.2 conditional trace repair

## Outcome

Repaired the URL-only workflow exposed by the real Codex acceptance run
`run_ms28su86_1f52f48fba9e`.

Codex correctly completed render, evaluation, and all eight resource reads, but the server's
unconditional three-tool instructions pushed it to call `ads_trace` without captured provenance.
The client invented `user-request` and a URL as file paths, and the validator correctly rejected
them with raw filesystem errors.

v0.2.2 keeps the validator strict while making trace applicability explicit:

- every run uses `ads_render -> ads_evaluate`;
- `ads_trace` is called only when the render manifest contains an observed skill file, source file,
  and artifact file;
- clients read the manifest and use exact captured paths and excerpts;
- prompt labels, placeholders, and URLs are never provenance;
- an inapplicable trace returns one actionable error without resolving the supplied paths.

## Implementation

- Replaced the unconditional initialization sequence with conditional trace instructions and kept
  the critical guidance inside the first 512 characters.
- Added exact-path descriptions to the trace input schema and strengthened the tool description.
- Added a manifest preflight before per-decision filesystem validation.
- Preserved the valid provenance-backed sequence without changing the three-tool public surface.
- Added both in-memory and packed-client regressions reproducing the exact Codex placeholder paths.
- Advanced package, Registry metadata, docs, tests, and the public `/mcp` contract page to v0.2.2.
